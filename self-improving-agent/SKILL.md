# self-improving-agent

一个用于**记录失败、纠正、知识缺口与可复用最佳实践**的执行型技能。
目标：把“出错后忘掉”变成“记录 → 复盘 → 提升 → 避免再次犯错”的闭环，同时避免把噪音写进长期记忆。

## 触发词
- 记一下这个教训 / 记住这个坑
- 这个错误以后别再犯
- 这个经验以后按这个做
- 用户纠正了我 / 知识过时了 / API 失败了
- self improve / learning loop / lessons learned

## 输入
- 当前失败、纠正、知识更新、最佳实践或新能力请求
- 可选项目路径 `--project <path>`
- 可选是否提升到公共区 `--public`
- 可选是否进一步写入 Minis 长期记忆

## 输出
默认返回：
1. 是否值得记录
2. 记录到哪一层（技能区 / 项目区 / 公共区 / Minis 记忆）
3. 建议使用的记录类别（learning / error / feature）
4. 如需提升，给出提升条件

## 核心原则
- **先判断值不值得记，再决定记到哪**
- **默认先写技能区 data/**
- **项目上下文明确时再写项目级 `.learnings/`**
- **确认跨任务复用后再提升到公共区或 Minis 记忆**
- **不要把一次性噪音、普通闲聊、临时失误都记进去**
- **测试/验证/演示产生的记录默认不进入正式 learnings 主层**
- **公共区只收稳定、已验证、非测试性质的条目**

## 记录层级
### L0：测试/验证记录
默认位置：`/var/minis/skills/self-improving-agent/data/testing/`
适用：
- 脚本联调
- promote / 版式 / 初始化 / 去重等机制测试
- demo 项目演示记录
- 暂不应进入正式技能 learnings 的实验性条目

规则：
- 默认不进入 `data/public/`
- 默认不提升到 Minis 长期记忆
- 只有在测试结果提炼出稳定规则后，才重新整理为正式 learning / error / feature

### L1：技能区 data/
默认位置：`/var/minis/skills/self-improving-agent/data/`
适用：
- 一般失败记录
- 用户纠正
- 知识缺口
- 新能力请求
- 尚未确认能跨任务复用的经验

### L2：项目级 `.learnings/`
仅在显式传入 `--project <path>` 时使用。
适用：
- 某个项目内特有的问题与经验
- 与该项目目录、脚本、配置强绑定的 learnings

### L3：技能内公共区 `data/public/`
适用：
- 跨项目可复用规则
- 反复出现的同类问题
- 已验证为通用最佳实践的经验

### L4：Minis 长期记忆
适用：
- 能浓缩成一句长期规则
- 跨会话、跨任务都稳定适用
- 已确认不是一次性背景知识

## 工作流

### 决策树
1. 先判断当前信息属于：失败、纠正、知识过时、最佳实践，还是功能需求。
2. 再判断这件事值不值得记录。
3. 值得记录时，优先写入技能区；有明确项目上下文再写项目级。
4. 若该经验跨任务复用、重复出现，提升到公共区。
5. 若能提炼成稳定长期规则，再考虑写入 Minis 记忆。

### 记录价值评分
给候选记录按证据打分：
- 非显然失败、需要排查才能定位：+3
- 用户明确纠正：+3
- 知识过时，需要更新做法：+3
- 可复用最佳实践：+3
- 同类问题重复出现：+2
- 仅一次性小失误：-2
- 普通闲聊 / 无复用价值：-3
- 用户明确说不要记录：直接不记录

建议阈值：
- `5+`：应记录
- `3~4`：可记录，视上下文决定
- `0~2`：一般不建议记录
- `<0`：不记录

### Phase 1: 判断是否值得记录
以下情况建议记录：
- 命令/操作失败且非显然
- 用户明确纠正
- 知识过时，需要纠偏
- 外部 API / 工具失败，且具复用价值
- 形成了更优、可复用做法
- 同类问题反复出现

以下情况一般不记录：
- 普通闲聊
- 一次性细枝末节
- 无复用价值的小失误
- 用户明确说“不要记录”

### Phase 2: 选择记录类别
- `learning`：纠正、知识缺口、最佳实践
- `error`：命令失败、异常输出、集成故障
- `feature`：用户提出的新能力需求
- `testing`：机制验证、联调、演示、版式/初始化/promote 测试记录

### Phase 3: 选择记录位置
- 默认先写技能区 `data/`
- 有明确项目上下文时，可写项目级 `.learnings/`
- 确认跨项目复用后，再提升到 `data/public/`
- 只有足够稳定时，才写 Minis 记忆

### 记录位置判断规则
- 当前问题强绑定某项目路径/仓库/配置：优先项目级
- 当前问题跨项目可复用，但还没到长期记忆级别：优先公共区
- 当前问题只是近期特例：先留在技能区或项目区，不急着提升
- 明显属于测试、演示、联调、机制验证：优先测试层 `data/testing/`

### 正式记录 vs 测试记录判定
以下情况默认判为测试记录，而不是正式 learnings：
- 条目摘要或详情主要描述“测试是否生效”“版式是否正确”“提升是否成功”
- 内容明显只是验证脚本机制，而非可复用工作规则
- 依赖 demo 项目、临时目录、演示输入
- 主要价值在于调脚本，而不是沉淀正式最佳实践

若测试记录最终提炼出稳定规则：
- 重新写一条正式 learning / error / feature
- 不直接把原测试条目 promote 到公共区

### Phase 4: 提升判断
满足以下任一条，才考虑提升：
- 能浓缩成一句“以后遇到 X 就做 Y”的规则
- 30 天内复发 ≥ 3 次，或出现在多个任务/项目
- 明确属于长期偏好、长期约定、长期工作规则

### 提升前检查点
提升到公共区或 Minis 记忆前，必须先检查：
- 这条是否本质上只是测试/演示记录
- 是否已脱离具体 demo / 临时目录 / 一次性脚本联调背景
- 是否已经能被改写成面对未来任务的稳定规则
- 是否存在更适合更新的已有公共条目，而不是新 promote

若以上任一项不满足：
- 不提升
- 先保留在当前层级或测试层

### 提升评分规则
- 跨项目复用：+3
- 30 天内复发 ≥ 3 次：+3
- 可浓缩成短规则：+2
- 当前仍明显依赖具体项目上下文：-2
- 仍未验证稳定性：-2

建议阈值：
- `6+`：可提升到公共区或 Minis 记忆
- `3~5`：先提升到公共区，不急着写 Minis 记忆
- `0~2`：保留在当前层级继续观察

### Phase 5: 状态更新
- `pending`：刚记录
- `in_progress`：正在处理
- `resolved`：已解决
- `promoted`：已提升到公共区或 Minis 记忆
- `wont_fix`：决定不处理

## 输出风格
- 默认先给短判断：记不记、记哪里、为什么
- 若值得记录，再给最小可执行动作
- 若不值得记录，直接说明“不建议记录”
- 若建议提升，再说明提升目标层级

## 响应模板
### 记录模板
- `这条值得记录，建议先写到技能区 learning/error 日志。`

### 不记录模板
- `这条暂时不值得进入长期学习记录，避免污染记忆系统。`

### 提升模板
- `这条已经具备跨任务复用价值，建议提升到公共区 / Minis 长期记忆。`

### 冲突模板
- `这条信息更像近期变化，不建议直接升格为长期规则。`

### 复发模板
- `这类问题已经重复出现，建议提高优先级并考虑提升到公共区。`

## 复发与去重规则
- 记录前优先搜索是否已有相似条目
- 若是相似问题复发：优先更新复发次数、最近出现时间，而不是盲目新增重复条目
- 若已存在公共区条目：不要重复 promote
- 若仍无法判断是否重复，先记录到当前层级，并建立 `See Also` 关联

## 失败与边界
- 不要把普通闲聊写进 learnings
- 不要把一次性背景信息直接写进 Minis 长期记忆
- 不要在没有项目上下文时乱写项目级 `.learnings/`
- 不要因为“看起来有道理”就直接提升到公共区
- 提升前应优先判断是否已复发、是否可复用、是否能短句表达
- 不要把 promote 测试、版式测试、初始化测试、demo 记录直接沉淀到公共区
- 不要让 data/public 变成脚本联调垃圾桶；公共区应只保留面向未来任务的稳定条目

## 入库/公开前清洗规则
在准备把 `self-improving-agent` 数据层纳入仓库、公开区或 shared 镜像前，先做清洗：
1. 删除或迁移纯测试条目到 `data/testing/`
2. 检查 `data/public/` 是否混入测试性 promote 结果
3. 把可复用规则改写成面向未来任务的正式表述
4. 避免 demo 路径、一次性目录名、临时验证语句直接进入公共区
5. 若无法快速判定是否应公开，默认先不入库数据层，只保留脚本与规则文档

- 提升条件清晰，不误升格
- learnings 能真正减少后续重复犯错
