# 总入口分流与调度系统

> 用于把 `nuwa-open-minis` 当前已有的输入识别、材料模式判断、原型路由、更新路径等能力，收束成统一入口调度系统。
> 目标不是增加流程感，而是让女娲在 Open Minis 中更像一个稳定的“总造 skill 路由器”，而不是只在人物型局部很强。

---

## 一、要解决什么问题
当前系统已经有：
- 输入类型识别
- 材料模式判断
- 人物 / 主题 / 岗位 / 更新区分
- 最小执行闭环

但仍容易出现以下问题：
- 路由分散在多个章节里，执行时容易漏
- 同一个任务同时命中多种路径时，不知道谁优先
- 模糊需求、明确需求、更新任务之间的入口动作不够统一
- “先调研”还是“直接写第一版”缺少统一裁决
- 人物型很强，但作为总调度器还不够稳

所以本文件要解决的是：
1. 先统一判断入口类型
2. 再统一判断材料模式
3. 再统一判断运行模式
4. 最后再进入具体原型生成

---

## 二、总调度顺序
默认按以下顺序调度：

1. **先判任务入口类型**
2. **再判是否新建 or 更新**
3. **再判材料模式**
4. **再判运行模式**
5. **再判 Skill 原型**
6. **最后进入具体执行骨架**

一句话：
> 先判“这是什么任务”，再判“用什么材料做”，再判“这轮怎么运行”，最后才判“Skill 写成什么样”。

---

## 三、第一层：任务入口类型
收到任务后，先分到以下 4 类之一：

### 1. 明确对象型
用户已经明确给出：
- 人物
- 主题
- 岗位
- 行业

例如：
- 蒸馏芒格
- 做个价值投资 Skill
- 造一个地市联通公众线助手 Skill

默认动作：
- 直接进入“明确对象路径”
- 不做长诊断
- 只在必要时追问 1 轮

### 2. 模糊需求型
用户没有明确对象，只说需求、困惑、目标。

例如：
- 我想提升决策质量
- 有没有一种思维方式能帮我做产品判断
- 我需要一个商业分析顾问

默认动作：
- 进入“需求诊断路径”
- 先做需求定位
- 最多推荐 2-3 个候选
- 用户选定后再进入生成

### 3. 更新补料型
用户已经有既有 Skill，要求：
- 更新
- 补强
- 喂新材料
- 修某个部分

例如：
- 更新这个 Skill
- 基于新材料补强表达 DNA
- 把校园市场部分继续养厚

默认动作：
- 优先读取已有目录与主文件
- 判断是增量更新还是结构重写
- 不默认从零重写

### 4. 审计对标型
用户不是要直接新造 Skill，而是要：
- 审计
- 对标原版
- 找差距
- 评估能否实现
- 做并排评审

例如：
- 再审计一遍女娲技能
- 对比原版，找差距
- 说出哪些能实现

默认动作：
- 优先进入评估路径，不直接重写
- 先出差距清单
- 再决定是否回写主文件或新增规范文件

---

## 四、第二层：新建 / 更新 / 审计裁决

### A. 新建
适用：
- 没有现成目录
- 用户明确要新造

动作：
1. 命名
2. 建目录
3. 先落 `SKILL.md`
4. 再决定是否补 research / README / REPORT / tests

### B. 更新
适用：
- 已有 Skill
- 用户要求补料、修订、增强

动作：
1. 先读取已有 `SKILL.md`
2. 判断本轮属于：补证据 / 补模块 / 修假像 / 修结构 / 加配套文件
3. 优先增量更新
4. 只有核心结构已变时才重写主骨架

### C. 审计
适用：
- 用户要评估，不是马上重做

动作：
1. 先读现版
2. 再读对照版 / 原版 / 样本
3. 形成差距清单
4. 按“可显式实现 / 只能长期逼近”分栏
5. 经用户确认后，再决定进入更新或补强

---

## 五、第三层：材料模式判断
在明确当前是新建 / 更新 / 审计后，再判断材料模式。

### 1. 纯本地材料模式
适用：
- 用户已上传足够材料
- 重点是内部材料、岗位材料、非公开材料蒸馏

动作：
- 优先只分析本地材料
- 不额外扩搜索，除非用户允许

### 2. 本地材料优先模式
适用：
- 用户有本地材料
- 但某些维度明显缺失

动作：
- 先吃透本地材料
- 再定向补外部信息
- 不让外部搜索盖过本地一手材料

### 3. 外部搜索补充模式
适用：
- 用户只给了名字或主题
- 没有提供本地材料

动作：
- 允许外部补充
- 但必须保留边界感
- 不把搜索摘要误当作高压研究

### 4. 纯目录内延续模式
适用：
- 当前 task 主要是对已有 Skill 目录继续补料 / 审计 / 修订
- 关键依据已经在当前 skill 目录里

动作：
- 优先读取当前 skill 目录内部文件
- 不重复大规模外搜
- 先吃透已有研究与评估文件，再决定是否补外部材料

默认优先级：
1. 当前 skill 目录内既有文件
2. 用户本地材料
3. 当前会话已沉淀结论
4. 必要的外部补充

---

## 六、第四层：运行模式判断
运行模式回答的是：这轮该怎么做，不是做什么。

### 1. 直接生成模式
适用：
- 用户明确要“直接造”“直接输出 SKILL.md”
- 主题足够清晰
- 信息虽不完美，但足以先出第一版

动作：
- 直接建目录
- 直接写第一版
- 缺口进入边界说明

### 2. 先调研后生成模式
适用：
- 用户明确要先看调研
- 主题复杂
- 风险较高，直接写容易空心

动作：
- 先走研究执行层骨架
- 先出调研检查点 / 提炼摘要
- 用户确认后再写主文件

### 3. 增量更新模式
适用：
- 已有 Skill
- 用户给新材料或新任务

动作：
- 不默认从零重写
- 先判断新材料属于：证据 / 锚点 / 表达 DNA / 张力 / 时间线 / 噪音
- 再定点回写

### 4. 审计后再落地模式
适用：
- 用户先要差距评估
- 还没同意进入补强

动作：
- 先形成审计清单
- 明确哪些能实现
- 等用户确认后，再进入文件补强

---

## 七、第五层：Skill 原型路由
完成前四层判断后，再决定写成哪类 Skill：

1. **人物视角型**
2. **主题导师型**
3. **行业 / 岗位助手型**
4. **已有 Skill 更新型**

原则：
- 原型决定正文结构
- 入口类型决定前置动作
- 两者不要混淆

例如：
- “我想提升决策质量” → 入口类型是模糊需求型，不是人物型
- 用户最终选芒格 → 原型才变成人物视角型

---

## 八、最小追问规则

### 可以直接默认推进
满足以下任一组合时，默认不追问：
- 对象明确 + 用户要直接生成
- 用户已给足材料 + 任务方向清楚
- 用户要更新现有 Skill + 更新点清楚
- 用户要审计对标 + 对照对象清楚

### 必须追问
只有以下情况才追问：
1. 无法命名 Skill
2. 用户同时给出多个冲突目标
3. 涉及私密 / 非公开人物，且材料不足
4. 用户既要“直接写”，又要“先调研确认”，目标冲突

规则：
- 最多 1 轮
- 追问后仍不清晰，则给最小可行版本或先做审计摘要

---

## 九、冲突裁决规则

### 冲突 1：用户说“直接生成”，但材料明显不足
裁决：
- 仍先落第一版
- 但明确边界
- 不因为不足就停在解释层

### 冲突 2：用户说“先调研”，但又要求立刻给最终版
裁决：
- 先给最小调研摘要
- 用户确认后再出最终版
- 不同时假装两者都完成了

### 冲突 3：已有 Skill 可增量修，但用户口头上说“重做”
裁决：
- 先判断核心结构是否真的失效
- 若未失效，优先增量修
- 不因“重做”二字就机械推翻已有结构

### 冲突 4：人物型规则很强，但当前其实是岗位型材料任务
裁决：
- 优先服从任务原型
- 不把岗位型任务强行人物化

### 冲突 5：目录工程化诉求很强，但当前只是快速小任务
裁决：
- 优先最短可用闭环
- 不机械开完整目录

## 十、统一执行模板
每次进入女娲任务时，脑内默认跑以下模板：

### Step 1：判入口类型
- 明确对象 / 模糊需求 / 更新补料 / 审计对标

### Step 2：判新建 / 更新 / 审计
- 是不是先读旧版？
- 是不是先做差距清单？
- 是不是先建目录？

### Step 3：判材料模式
- 目录内已有 / 本地材料 / 本地优先 / 外部补充

### Step 4：判运行模式
- 直接生成 / 先调研 / 增量更新 / 审计后落地

### Step 5：判 Skill 原型
- 人物 / 主题 / 岗位 / 更新型

### Step 6：进入对应骨架
- 研究执行层
- 目录工程化
- 人物型规则
- 持续喂料
- 假像识别
- 回归机制

---

## 十一、和其他文件的分工
- **本文件**：负责统一入口分流与调度
- `研究执行层标准骨架.md`：负责研究阶段怎么跑
- `目录级自包含工程化标准.md`：负责目录怎么做成长期容器
- `人物型假像识别清单.md`：负责识别人物型哪里假了
- `人物型持续喂料与增量收敛机制.md`：负责补料后怎么继续收敛

顺序建议：
1. 先按本文件完成总路由
2. 再按研究执行层决定要不要开研究骨架
3. 再按目录工程化决定要不要补全目录容器
4. 再进入具体原型规则与回归机制

---

## 十二、最终原则
- 总入口调度的目标，是减少漏判与错路由
- 不同任务先分流，再生成；不要一上来就套模板
- 人物型强，不等于女娲总入口就强；总入口必须能覆盖模糊需求、更新、审计、岗位型任务
- 调度系统越稳定，后面的研究、写作、回归才越不会乱
