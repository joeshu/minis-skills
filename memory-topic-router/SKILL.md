# memory-topic-router

一个用于**优先命中专题记忆**的执行型技能。
目标：当任务与某个主题、站点、项目、工作流、方法论或高频来源明显相关时，先读取专题记忆文件，再决定是否补查 `GLOBAL.md` 与 daily memory，减少无关检索噪音并提高命中质量。

## 触发词
- 专题记忆 / topic memory / memory topic
- 先查专题 / 先查项目记忆 / 先看主题规则
- 记忆维护 / 记忆系统 / skill 设计 / 方法论
- 某项目、某站点、某工作流、某固定来源的长期规则

## 输入
- 当前任务描述
- 可选主题名、项目名、站点名、工作流名
- 可选目标：执行任务 / 记忆维护 / skill 优化 / 方法论回顾

## 输出
默认返回：
1. 是否命中专题记忆
2. 命中的专题文件路径
3. 若未命中，后续回退到哪里检索
4. 最终建议采用的记忆来源顺序

## 核心原则
- **专题记忆优先于通用记忆**
- **显式提到主题时优先查专题**
- **即使用户没直接说专题名，只要有明显语义/站点/路径/工作流关联，也应优先考虑专题记忆**
- **专题不足时再回退到 `GLOBAL.md` 与 daily memory**
- **当前用户指令优先于历史记忆**
- **本技能只负责“先读哪层”，不负责决定新信息写到哪层**

## 记忆层级
### L1：专题记忆（优先）
位置：`/var/minis/shared/memory_topics/`
适用：
- 某个项目
- 某个站点 / 平台
- 某个工作流
- 某种方法论
- 某类高频来源

### L2：GLOBAL.md（通用总原则）
适用：
- 跨主题共享规则
- 通用执行偏好
- 安装约束
- 结果验证规则
- 决策边界

### L3：daily memory（近期变化）
适用：
- 最近新增约定
- 路径调整
- 临时偏好变化
- 时间线增量

## 工作流

### 决策树
1. 先看当前任务是否命中明确主题、站点、项目、工作流、方法论、高频来源。
2. 若命中，优先检查 `/var/minis/shared/memory_topics/` 下是否存在同名或高相关专题文件。
3. 若专题文件存在，先读专题文件。
4. 若专题文件不存在，或内容不足，再补查 `GLOBAL.md`。
5. 若任务涉及近期变动、路径调整、最新约定，再按需补查 daily memory。
6. 若当前用户要求与专题规则冲突，优先遵循当前指令，并视情况更新专题或 daily memory。

### 匹配优先级
专题候选的判断优先级如下：
1. **显式命中**：用户直接说出项目名 / 站点名 / 工作流名 / 方法论名
2. **路径命中**：任务中出现稳定目录、仓库路径、固定文件结构
3. **站点命中**：任务明显针对 GitHub、某内容平台、某固定来源
4. **工作流命中**：任务与固定协作流程、固定执行链强相关
5. **方法论命中**：任务属于记忆维护、skill 设计、本地化、上下文压缩等长期方法论主题
6. **语义命中**：用户没直说主题名，但语义高度接近某长期主题

### Phase 1: 识别专题候选
优先从以下信号识别专题：
- 用户直接说出项目名 / 站点名 / 技能名 / 工作流名
- 任务中出现稳定路径、固定站点、固定平台、固定来源
- 明显属于某个方法论主题（如记忆维护、skill 设计、本地化、上下文压缩）
- 与历史高频来源强相关（如 GitHub、某项目仓库、某内容平台）

### Phase 2: 优先读取专题记忆
候选专题命中后：
1. 先检查 `/var/minis/shared/memory_topics/` 是否存在同名或高相关文件
2. 若存在，先读取该文件
3. 将专题文件作为当前任务的首选记忆依据

### 专题文件发现规则
优先按以下顺序寻找专题文件：
1. **完全同名命中**：如项目名、站点名、方法论名直接对应文件名
2. **别名命中**：如仓库名、平台常用简称、工作流简称
3. **语义高相关命中**：文件名虽不完全相同，但主题高度接近
4. **目录层级命中**：如按主题子目录组织的专题文件

### 多候选专题处理
如果同时命中多个高相关专题：
- 优先级：项目专题 > 工作流专题 > 平台专题 > 方法论专题
- 若当前任务明显属于某一执行链，则优先最贴近当前动作的专题
- 若多个专题都可能相关，可先读取最具体的那个，再视需要补读上层专题

### 专题不足评分
判断专题文件是否足够支持当前任务时，可按以下标准加分：
- 包含当前任务直接相关规则：+3
- 包含当前路径/平台/项目的稳定约定：+2
- 包含当前工作流执行步骤：+2
- 包含近期仍有效的结论：+2
- 只有背景介绍、缺执行规则：-3
- 内容明显过时：-2
- 与当前任务只弱相关：-2

建议阈值：
- `5+`：可直接作为主依据
- `3~4`：可先读取，再补查 `GLOBAL.md` 或 daily memory
- `0~2`：专题不足，应回退

### 专题类型区分
- **项目专题**：记录某个项目的长期约定、路径、验证方式、特殊流程
- **站点/平台专题**：记录某个平台、站点、来源的长期规则、入口、限制
- **工作流专题**：记录某套固定执行流程、协作流程或操作顺序
- **方法论专题**：记录跨项目但属于某方法论主题的稳定规则

### Phase 3: 回退规则
仅在以下情况下回退：
- 专题文件不存在
- 专题文件内容明显不足以支持当前任务
- 当前任务需要跨主题总原则
- 当前任务涉及近期更新、路径变化、最新例外

### 专题不足判定标准
满足任一即可视为“专题不足”，需要补查 `GLOBAL.md` 或 daily memory：
- 专题文件只覆盖背景，不覆盖当前执行规则
- 专题文件没有当前任务所需的关键路径、约束或工作流
- 专题规则与当前任务明显不完全匹配
- 专题文件未记录近期变动，而当前任务明显依赖近期变化
- 专题文件存在，但内容过旧或缺少当前主题下的稳定结论

回退顺序：
1. `GLOBAL.md`
2. daily memory

### Phase 4: 冲突处理
- 当前用户明确要求 > 专题记忆 > GLOBAL.md > daily memory 的旧约定
- 若当前任务已经出现新特例或新规则，应视情况更新专题或 daily memory

### Phase 5: 专题维护规则
- 专题文件用于沉淀**主题内稳定知识与工作流**
- `GLOBAL.md` 用于跨主题总原则
- daily memory 用于近期变化与时间线增量
- 方法论细则优先沉淀到对应方法论专题文件
- 不把一次性临时变化直接写成专题长期规则

### 更新去向规则
- **稳定、可复用、主题内长期有效** → 更新专题文件
- **跨主题共享的长期原则** → 更新 `GLOBAL.md`
- **近期变化、临时偏好、路径调整、时间线增量** → 写入 daily memory
- **当前用户提出新特例，但尚未验证是否长期有效** → 先写 daily memory，不急着升格为专题规则

## 专题优先命中规则
以下任一成立，应优先查专题记忆：
- 明确主题命中：项目名、站点名、工作流名、方法论名
- 语义命中：任务含义明显属于某专题
- 站点命中：任务直接针对固定站点或平台
- 路径命中：任务涉及某稳定目录或固定路径结构
- 历史工作流命中：任务复用某长期固定流程

## 输出风格
- 命中专题时：先说“已命中专题记忆”，再说明文件路径
- 专题不足时：简短说明“专题不足，补查通用/近期记忆”
- 未命中时：直接说明“未找到专题文件，回退到 GLOBAL.md / daily memory”
- 不默认展开大量检索过程

## 响应模板
### 命中专题模板
- 结论：`已命中相关专题记忆。`
- 路径：给出专题文件路径
- 动作：说明将优先按该专题规则执行

### 回退模板
- 结论：`未找到足够的专题记忆。`
- 动作：说明将继续补查 `GLOBAL.md` 或 daily memory

### 冲突模板
- 结论：`当前用户要求与历史专题规则不同。`
- 动作：说明会优先遵循当前要求，并视情况更新记忆

### 维护模板
- 结论：`当前规则更适合写入专题 / GLOBAL / daily 中的某一层。`
- 动作：说明建议写入哪一层，以及为什么

## 专题命名建议
- 项目专题：`<project>.md` 或 `<project>-topic.md`
- 平台专题：`github.md`、`xiaohongshu.md`、`bilibili.md`
- 工作流专题：`github-sync.md`、`memory-maintenance.md`
- 方法论专题：`skill-design.md`、`context-compaction.md`

命名原则：
- 尽量短、稳定、可预测
- 同一主题避免多个近义文件并存
- 若已有主专题文件，优先更新该文件，不重复新建变体

### 专题维护检查清单
维护专题文件前，优先检查：
- 当前规则是否属于长期稳定知识
- 是否真的只属于该主题，而不是跨主题总原则
- 是否只是近期临时变化
- 是否已有同主题主文件可更新
- 是否会造成多个近义专题文件并存

## 风险与反例
- 不检查专题文件，直接去 daily memory，导致命中噪音
- 用户没直说专题名，就错误地跳过专题检索
- 专题文件存在却不用，直接套通用规则
- 当前用户提出新要求时，错误地被历史专题规则绑死
- 把近期临时变化误写成通用长期规则

## 与 session-context-compactor 的分工
- `memory-topic-router` 负责：**任务开始前或执行中，决定先查哪类长期记忆**。
- `session-context-compactor` 负责：**把当前长会话压缩为可继续执行的 handoff**。
- 前者面向长期记忆检索顺序；后者面向当前会话收尾与交接。
- 如果任务是“继续某个项目，先按过去约定来”，优先用 `memory-topic-router`。
- 如果任务是“当前会话太长，帮我整理成交接摘要”，优先用 `session-context-compactor`。

## 与 open-minis-memory-store 的分工
- `memory-topic-router` 负责：**在任务开始前或执行中，决定先查哪类记忆**。
- `open-minis-memory-store` 负责：**把分散记忆整理成主记忆，并清理旧记忆**。
- 前者是检索顺序路由器；后者是记忆治理与归并器。
- 如果任务是“继续某项目先按过去约定来”，优先用 `memory-topic-router`。
- 如果任务是“把这个主题的记忆收拢成一条并删旧版本”，优先用 `open-minis-memory-store`。

## 测试要求
至少覆盖：
1. 明确项目名命中特定专题
2. 用户未说专题名，但语义明显命中专题
3. 专题不存在时回退到 GLOBAL.md / daily memory
4. 方法论主题命中专题文件
5. 当前用户要求覆盖专题旧规则
