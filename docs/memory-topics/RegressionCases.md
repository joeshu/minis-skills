# 回归样本集

## 目的
- 用真实问题样本验证这套体系是否真的提升输出与执行质量，而不是只在规则层自洽。
- 建立 baseline 与 governed 输出的对照基础，避免规则越加越多却收益不明确。

## 使用原则
- 样本优先来自真实会话中的高频问题、失败问题、边界问题。
- 样本用于回归，不用于堆砌规则。
- 若某失败只出现一次，优先留在样本层，不急于升级为系统规则。

## 初始回归维度

### 1. 简单问答
- 是否首句直接给结论
- 是否避免无意义铺垫
- 是否没有因过度简化漏掉必要信息

### 2. 技术解释 / 报错分析
- 是否结论先行
- 是否保留必要 caveat
- 是否把可能性说成确定性

### 3. 执行任务
- 是否给出命令、路径、改法
- 是否没有教程化扩写
- 是否在简洁与可执行性之间取得平衡

### 4. 比较与选型
- 是否先给结论
- 是否只列关键差异
- 是否避免堆近似方案

### 5. 搜索 / 网页任务
- 是否先走正确路由
- 是否避免不必要重读与过度检索
- 是否控制读取成本

## 初始样本占位

### Case 1
- 类型：体系维护
- 输入：这套系统与技能有什么区别
- baseline 输出特征：容易从抽象概念出发，讲很多管理学式比喻，结论较晚出现
- governed 输出特征：先给结论“系统是治理层，技能是任务层”，再用 4~5 个关键维度压缩说明
- 主要差异：定义更快收束，层级关系更清楚，避免过多抽象铺垫
- baseline 评分：6/10（推测）
- governed 评分：9/10
- 是否通过：是
- 若未通过，失败模式归类：无
- 是否需要升格为规则：否

### Case 2
- 类型：体系维护
- 输入：这套系统与全局md与专题md是一套吗
- baseline 输出特征：可能把 GLOBAL、专题文件、系统本体混讲，导致层级边界不清
- governed 输出特征：先给结论“是同一套，但不是同一层”，再拆成全局默认层 / 专题规则层 / 系统运行层
- 主要差异：结构边界更清楚，避免把入口文件与系统整体混为一谈
- baseline 评分：6/10（推测）
- governed 评分：9/10
- 是否通过：是
- 若未通过，失败模式归类：无
- 是否需要升格为规则：否

### Case 3
- 类型：执行任务
- 输入：请帮我推送到git吧。环境里有token
- baseline 输出特征：可能先长篇说明上传策略、风险和步骤，再进入执行
- governed 输出特征：先检查 token 与本地仓库，再克隆、sync、push，并只提交目标子目录
- 主要差异：执行闭环优先，解释从属，符合 OpenMinis 可执行任务优先原则
- baseline 评分：5/10（推测）
- governed 评分：10/10
- 是否通过：是
- 若未通过，失败模式归类：无
- 是否需要升格为规则：否

### Case 4
- 类型：执行任务
- 输入：向上同步好同步，但是恢复到本机，请说说
- baseline 输出特征：可能偏概念解释，恢复策略与实际恢复动作分离
- governed 输出特征：先给恢复原则，再明确 restore-check / restore-sync 的安全恢复路径，并把 GLOBAL 与 daily memory 区分开
- 主要差异：恢复逻辑更贴近实际工作流，文件落点与备份路径更明确
- baseline 评分：6/10（推测）
- governed 评分：9/10
- 是否通过：是
- 若未通过，失败模式归类：无
- 是否需要升格为规则：否

### Case 5
- 类型：体系维护
- 输入：审计这一整套系统。找出问题。更科学，更符合逻辑，更好用，更适合openminis
- baseline 输出特征：可能继续泛泛谈“还可以优化”，但不区分系统级问题与文件级问题
- governed 输出特征：先给终审结论，再聚焦样本层偏空、总纲层略重、目录双轨、OpenMinis 执行语境不足四类系统问题，并给最小优化动作
- 主要差异：审计对象从单文件上升到系统层，问题更聚焦，优化动作更小而有效
- baseline 评分：7/10（推测）
- governed 评分：9/10
- 是否通过：是
- 若未通过，失败模式归类：无
- 是否需要升格为规则：否

## OpenMinis 优先样本方向
- 样本优先补以下场景：
  - 可直接执行而不应先长解释的任务
  - 需要决定结果落点（chat / workspace / shared / memory）的任务
  - 工具调用预算容易失控的任务
  - 路由错误比表达错误更影响结果的任务
