# 废弃与合并机制

## 目的
- 让这套体系不只会增长，也会收缩。
- 规定哪些文件、规则或命名应被合并、下沉、废弃或只保留兼容入口。

## 核心原则
- 规则系统应优先保持主定义清晰，而不是文件数量持续增加。
- 废弃不是删除历史，而是明确主入口与非主入口。

## 适用场景
- 两个文件长期承担相近职责
- 某旧文件已被新文件吸收
- 某文件只剩样本价值，不再承担核心规则职责
- 某命名继续存在但不宜作为主入口

## 处理动作

### 1. 合并
适用：两个文件职责高度重叠。
- 保留一个主文件
- 另一个文件内容并入主文件
- 被合并文件可保留短说明，标注已并入何处

### 2. 废弃
适用：文件不再作为核心入口，但仍需保留历史兼容。
- 在文件头部说明：已废弃 / 建议改读哪个文件
- 不再继续扩写正文

### 3. 下沉为样本
适用：内容对系统规则价值不高，但有案例价值。
- 从核心规则入口移出
- 保留在样本层或 README 样本区

### 4. 删除
适用：重复、错误、无历史价值且无兼容需求。
- 删除前应确认已在其他位置保留必要信息

## 判定标准
满足以下任一项，可考虑合并或废弃：
- 职责重叠度高于 70%
- 被更高层文件完全吸收
- 长期不再作为读取入口
- 继续保留只会增加理解成本
- 长期无回归样本支撑，且未被索引主路径使用

## 不宜废弃的对象
- 当前体系主入口文件
- 冲突裁决、路由、预算、验收这类核心治理文件
- 仍被索引明确指向的主文件，除非已同步更新索引

## 执行要求
- 合并或废弃后，要同步更新：
  - `TopicIndex.md`
  - `SystemArchitecture.md`
  - 相关 metadata
  - 必要时更新回归样本与失败模式引用
